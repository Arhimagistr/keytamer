## 1. РЕЗЮМЕ И КЛЮЧЕВЫЕ ВЫВОДЫ

1. Экономический закон абстракций (Fowler / Metz):
   Абстракция — это не бесплатный инструмент чистоты, а долговое обязательство. Любая спекулятивная абстракция облагается налогом владения (Cost of Carry), задерживает выпуск ценности (Cost of Delay) и неизбежно переписывается при столкновении с реальностью (Cost of Repair).

2. Баланс простого дизайна (Kent Beck):
   Правило «Fewest elements» (минимальное число сущностей) является фильтром против догматичного DRY. Дублирование кода на ранних этапах намного дешевле ошибочной абстракции (Sandi Metz). До достижения порога Rule of Three (3 реальных потребителя) дублирование изолировано и безопасно.

3. Борьба с поверхностными модулями (John Ousterhout):
   Главный враг кодовой базы — не размер файлов, а синдром «Classitis» (нарезка на десятки мелких классов-прокладок) и мелкие модули (Shallow Modules), у которых сложность интерфейса сопоставима со сложностью реализации. Модули должны быть глубокими (Deep Modules): максимальная инкапсуляция за минимальным интерфейсом.

## 3. КАТАЛОГ АНТИПАТТЕРНОВ ОВЕРИНЖИНИРИНГА

1. Speculative Generality:
   - Создание интерфейсов и протоколов с 1 конкретной реализацией (1:1 pair).
   - Сигнатуры «на вырост» (`*args`, `**kwargs`, неиспользуемые `options=None`).
   - Паттерны «Фабрика фабрик» при отсутствии множественных провайдеров.

2. Pass-Through Wrappers:
   - Классы и функции, единственная задача которых — перенаправить аргументы в следующий слой (`return self._inner.call(a, b)`).
   - Искусственное разделение на Controller -> Service -> Manager -> Repository без добавления доменной логики между ними.

3. Configuration Bloat:
   - Вынос констант приложения в YAML/.env ради «гипотетической гибкости».
   - Утрата типобезопасности, раздутие кода валидации и разрыв связей при анализе кода.

4. Premature Micro-modularization:
   - Дробление логики на файлы по 10–20 строк под лозунгом «один класс — один файл».
   - Усложнение ментальной модели, взрывной рост импортов и накладных расходов.

5. Mock-Driven Interface Pollution:
   - Интерфейсы, созданные исключительно как подпорка для unit-тестов.
   - Игнорирование возможностей современного прямого тестирования и in-memory тестовых дублеров.

## 4. СТАТИЧЕСКИЕ МЕТРИКИ И ДЕТЕКТОРЫ (ДЛЯ YAGNI_GUARD)

```
                       ┌──────────────────────────────┐
                       │      yagni_guard (AST)       │
                       └──────────────┬───────────────┘
                                      │
         ┌────────────────────┬───────┴────────────┬────────────────────┐
         ▼                    ▼                    ▼                    ▼
   [Fan-In Check]       [SIIT Detector]     [Dead Params]       [Pass-Through]
  Fan-in = 0 (Dead)    Interface with 1     Unread arguments    Pure single-call
  Fan-in = 1 (Inline)   implementation      in ast.FunctionDef   return delegators
```

1. Метрика Fan-In:
   - $Fan\text{-}in = 0$: Мертвый код -> удаление.
   - $Fan\text{-}in = 1$: Single-Consumer -> рекомендация: inline в место вызова.
   - $Fan\text{-}in \ge 3$: Зеленая зона соответствия Rule of Three.

2. Single-Implementation Interface Trap (SIIT):
   - AST-поиск `abc.ABC`, `typing.Protocol`, `interface`.
   - Если в пределах проекта число наследников $N_{impl} == 1$, выдается предупреждение об избыточной абстракции.

3. Dead Parameter Detector:
   - Вычисление разности между объявленными параметрами функции и идентификаторами, загружаемыми (`ctx=ast.Load()`) в теле функции.

4. Pass-Through Detector:
   - Выявление функций, чье тело состоит ровно из одного выражения возврата прямого делегированного вызова без модификации аргументов и обработки ошибок.

5. Shallow Module Index (SMI):
   - $SMI = \frac{\text{Интерфейсная сложность}}{\text{Глубина реализации}} = \frac{N_{\text{public\_methods}} + N_{\text{params}}}{SLOC_{\text{logic}} + CyclomaticComplexity}$.
   - При $SMI > 0.4$ модуль квалифицируется как поверхностный и рекомендуется к слиянию.

### 5.2. 4-фазный регламент исполнения
1. Pre-Implementation Gate:
   - Проверка Rule of Three до написания кода.
   - Фильтрация спекулятивных требований (срок востребованности > 24 часов).
2. Implementation Limits:
   - Запрет интерфейсов с одной реализацией.
   - Inline-First правило для локальных функций.
   - Максимум 3 уровня вызовов до доменного ядра.
3. Code Review Checklist:
   - Детекция прокладок, мертвых параметров и раздутых конфигов.
4. Cleanup Protocol:
   - Декомпозиция в сторону упрощения: Inline Method, Inline Class, Coalesce Files, De-config.
