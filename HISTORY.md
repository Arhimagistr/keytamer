# Keytamer — Architectural Decisions & History

> **SSOT of decisions made, pivots, and learnings.**

## 2026-10-23 ADR-001: Безопасная вставка диктовки через буфер обмена (⌘V)

- **Context:**  
  Пользователь обнаружил, что при записи голосовых сообщений распознанный текст нередко вставляется обрывисто (не полностью), хотя в окне истории Keyboop транскрипт сохраняется полностью.
  Причина: в Keyboop вставка диктовки производилась посимвольной эмуляцией набора (`TextReplacer.typeUnicode`) пачками по 12 символов с задержкой 800 мкс (~15 000 симв/сек) через `CGEvent`. В современных приложениях (Telegram, Slack, Chrome, VS Code) на длинных фразах (>150–200 знаков) очередь событий переполняется или React/DOM сбрасывает фокус, что приводит к отбрасыванию части символов.
- **Decision:**  
  Внедрен метод `TextReplacer.pasteViaClipboard`, использующий системное сочетание `⌘V`:
  1. Перед вставкой делается полный снимок всех типов данных из `NSPasteboard.general` (с сохранением исходного порядка типов).
  2. Текст диктовки временно записывается с тегом `org.nspasteboard.TransientType` (игнорируется менеджерами буфера Paste, Maccy и др.).
  3. Отправляется синтетический `⌘V`.
  4. Через 250 мс восстанавливается оригинальное содержимое буфера пользователя (при условии, что `changeCount == ours`).
  5. В настройки добавлен тумблер `voiceClipboardPaste` и настраиваемый порог символов `voiceClipboardThreshold` (0 = всегда, пресеты 30/60/100, либо произвольное число).
- **Alternatives Considered:**  
  - Увеличение задержки `usleep` между чанками: замедляет вставку и не гарантирует устранение дропа в Electron при сложных DOM-структурах.
  - Слепая вставка через `⌘V` без восстановления буфера (Punto-стиль): нарушает фундаментальный принцип Keyboop Zero Clipboard Pollution.
- **Consequences:**  
  - 100% стабильность вставки длинных надиктованных текстов в любые приложения без обрывов.
  - Полное сохранение пользовательского буфера обмена.

## 2026-10-24 ADR-002: Быстрое переключение языка распознавания речи и инвертированный статус-бейдж

- **Context:**  
  При работе с двуязычным вводом пользователь сталкивался с ситуацией, когда Whisper генерировал транслитерированную бессмыслицу при несовпадении языка речи и активной раскладки (или при неточном автоопределении акустической моделью). Требовался быстрый способ переключения языка диктовки без открытия настроек и четкая визуальная индикация активного режима в строке меню.
- **Decision:**  
  1. Добавлено быстрое действие `switchVoiceLanguage` в перечень `QuickAction.rightClickOptions`. По правому клику на иконку Keyboop в строке меню происходит циклическое переключение `auto -> ru -> en -> auto` с всплывающим информационным тостом `VoiceIndicator.shared.showToast`.
  2. Разработан генератор адаптивных инвертированных бейджей `MenuBarController.badgeImage(text:)`: отрисовывается сплошная плашка со скруглением углов `xRadius: 3.5`, текст вырезается через `CGBlendMode.destinationOut`, а изображению присваивается `isTemplate = true`. В темной теме macOS плашка становится белой с черными полыми буквами `RU` или `EN`.
  3. В режиме `voiceLanguage == "auto"` язык транскрипции определяется по скрипту активной раскладки (`dictationScript`: латиница -> `en`, кириллица -> `ru`).
  4. При включенной опции `voiceAutoSwitchLayout` смена системной раскладки перед записью диктовки сразу фиксирует актуальный `dictationScript`, исключая использование устаревшего состояния.
  5. В основное меню строки состояния добавлено подменю «Язык диктовки» для наглядного выбора режима левым кликом.
- **Consequences:**  
  - Мгновенное переключение языка распознавания в один клик мыши без разрыва рабочего контекста.
  - Высококонтрастная нативная индикация выбранного языка диктовки в строке меню.
  - Полная ликвидация фонетической каши при диктовке в смешанных сценариях.

## 2026-10-24 ADR-003: Временный оверрайд языка по модификатору, тумблер voiceFollowLayout и полупрозрачная подложка индикатора

- **Context:**  
  Пользователь указал на избыточность насильного переключения раскладки перед записью (`voiceAutoSwitchLayout`) и сформулировал чистую иерархию приоритетов:
  1. Жестко выбранный язык диктовки (`ru`/`en`) отменяет любые привязки.
  2. В режиме `auto` пользователь должен иметь явный тумблер включения/выключения привязки к раскладке.
  3. Для быстрой надиктовки англоязычных фраз без смены глобального режима нужен временный оверрайд языка по нажатию клавиши-модификатора (по умолчанию `⌘` Command) вместе с текущим хоткеем диктовки.
  4. Индикатор в строке меню при `menuBarStyle == "hidden"` должен сохранять исходный привычный шрифт текста `Ru` / `En`, дополняясь лишь легкой полупрозрачной скругленной подложкой белого цвета при зафиксированном языке.
  5. Поле порога вставки через буфер обмена должно деактивироваться при выборе режима «Все тексты».
- **Decision:**  
  1. Удален `voiceAutoSwitchLayout`. Введен тумблер `voiceFollowLayout` (по умолчанию `true`), вынесенный первым пунктом в подменю диктовки строки меню и в окно настроек.
  2. Реализован временный оверрайд языка диктовки: если при нажатии/удержании хоткея диктовки зажат модификатор оверрайда (`voiceOverrideModifier`, по умолчанию `Command`), запись помечается как `isOverrideDictation`, и Whisper/Parakeet расшифровывают речь на языке подмены (`voiceOverrideLanguage`, по умолчанию `en`).
  3. В `EventTap` добавлена фильтрация аккордов: добавление оверрайд-модификатора к клавише диктовки не считается посторонним аккордом и не обрывает запись.
  4. Создан генератор `MenuBarController.badgeWithPlate(text:)`: отрисовывает системным шрифтом статус-бара текст `Ru` / `En` поверх скругленной прямоугольной подложки с повышенной прозрачностью (22% альфы), сохраняя нативный стиль macOS.
  5. В `SettingsWindow.swift` при `voiceClipboardThreshold == 0` поле деактивируется (`isEnabled = false`) со значением «—».
  6. Добавлен звуковой сигнал `Tink` при смене языка и тумблеров в строке меню.
- **Consequences:**  
  - Чистая, предсказуемая иерархия без вмешательства в пользовательскую раскладку.
  - Мгновенная диктовка на английском через `⌘ + хоткей` без кликов и переключений.
  - Высокая визуальная согласованность меню-бара с нативным интерфейсом.

## 2026-10-25 ADR-004: Ребрендинг в Keytamer, bundle id com.keytamer.tamer и публичный репозиторий

- **Context:**  
  Принято решение о самостоятельном развитии проекта под брендом Keytamer с публикацией в независимом публичном репозитории GitHub (`Arhimagistr/keytamer`).
- **Decision:**  
  1. Полный ребрендинг проекта: приложение именуется `Keytamer`, идентификатор бандла — `com.keytamer.tamer` (dev: `com.keytamer.tamer.dev`).
  2. Исходный проект `/Users/manar/AIII/projects/keyboop` сохраняется в неизменном изолированном виде, разработка перенесена в `/Users/manar/AIII/projects/keytamer`.
  3. В файле LICENSE зафиксирован единственный копирайт: `Copyright (c) 2026 Arhimagistr`.
  4. Все сборочные скрипты (`build-app.sh`, `install-local.sh`, `Package.swift`), entitlements и исходный код переведены на пути `Sources/Keytamer` и бандл `Keytamer.app`.
  5. Сформирована чистая хронологическая история коммитов Git для демонстрации логики развития возможностей с самого начала проекта.
- **Consequences:**  
  - Полная независимость проекта, публичная кодовая база на GitHub.
  - Изоляция настроек и прав TCC/Accessibility от прежних версий.

## 2026-10-25 ADR-005: Устранение дефектов totals-critic (P0 модификатор оверрайда, изоляция хранилища, P1 буфер и параллелизм)

- **Context:**  
  В ходе 5-эшелонного состязательного аудита `totals-critic` выявлены 2 блокирующих дефекта P0 и дефекты протоколов P1:
  1. `EventTap.swift`: преждевременный сброс флага `voiceModArmed = false` при отпускании хоткея диктовки с зажатым модификатором оверрайда (`Command`). В режиме `toggle` подмена языка никогда не срабатывала.
  2. Фрагментация путей `Application Support`: замок блокировки процесса брался в `Keytamer/singleton.lock`, а зашифрованная история `VoiceHistory` и маркер `voice-busy` обращались к легаси-каталогу `Keyboop/`. Это создавало риск одновременного запуска двух инстансов с активными `CGEventTap` и разрушения ввода пользователя.
  3. `TextReplacer.swift`: при восстановлении пользовательского снапшота буфера ошибочно выставлялся маркер `org.nspasteboard.TransientType`, из-за чего внешние утилиты буфера (Maccy, Raycast, Alfred, Paste) удаляли пользовательские данные.
  4. `TextReplacer.swift`: метод `pasteViaClipboard` выполнялся на `DispatchQueue.main` без координации с очередью синтетики `synthQueue`, допуская перемешивание пакетов Backspace/Unicode с `⌘V`.
- **Decision:**  
  1. В `EventTap.swift` при очистке взвода хоткея диктовки вычитать маску активного модификатора оверрайда (`overMod`).
  2. Унифицировать все пути хранилища на `Application Support/Keytamer`. Добавить в `VoiceHistory` прозрачную однократную миграцию `history.enc` из `Keyboop` при его отсутствии в `Keytamer`. В `AppDelegate.swift` проверять как `Keytamer/singleton.lock`, так и `Keyboop/singleton.lock` для исключения параллельного запуска с оригинальным Keyboop.
  3. В `TextReplacer.swift` исключить установку `TransientType` на восстанавливаемые элементы буфера пользователя.
  4. Сериализовать выполнение `pasteViaClipboard` через `synthQueue` с синхронным переходом на главный поток для обращений к `NSPasteboard`.
- **Consequences:**  
  - Полная надежность временного оверрайда языка по хоткею.
  - Исключение конфликтов и гонок с легаси-процессами.
  - Сохранение пользовательского буфера обмена без потерь и гарантированный порядок синтетических клавиатурных событий.

## 2026-10-25 ADR-006: Полный ребрендинг кодовой базы под бренд Keytamer и изоляция ресурсов (Батч 1)

- **Context:**  
  Аудит кодовой базы выявил свыше 350 остаточных упоминаний легаси-имени `Keyboop` и `ru.keyboop.app` в идентификаторах связки ключей Keychain, системных логах, именах ресурсов (`keyboop-logo-anim.mp4`), именах модулей (`KeyboopMark.swift`) и служебных константах. Это нарушает архитектурную чистоту независимого бренда Keytamer и создает риск рассогласования настроек.
- **Decision:**  
  1. Переименовать модуль `KeyboopMark.swift` в `KeytamerMark.swift` с заменой структурного типа `KeyboopMark` на `KeytamerMark`.
  2. Перевести все строки онбординга и сборочные скрипты на нативный логотип `keytamer-logo-anim.mp4`.
  3. Унифицировать префиксы системных логов: `kbLog` перенаправить на префикс `[Keytamer]`, исключая разрыв существующих контрактов вызова.
  4. Заменить легаси-идентификаторы `ru.keyboop.app` и сервисы Keychain на `com.keytamer.tamer` с прозрачной миграцией учетных данных при их наличии.
  5. Сохранить неблокирующую проверку `Keyboop/singleton.lock` исключительно в защитных целях (предотвращение одновременного запуска двух конкурирующих приложений).
- **Consequences:**  
  - 100% изоляция идентификаторов, логов и ресурсов Keytamer.
  - Устранение риска коллизий с установленными в системе легаси-версиями.

## 2026-10-25 ADR-007: YAGNI-рефакторинг, слияние поверхностных модулей и ликвидация рассогласования кортежей (Батч 2)

- **Context:**  
  Аудит кодовой базы по принципам YAGNI и Simple Design (Kent Beck, Sandi Metz, John Ousterhout) выявил:
  1. Поверхностный микрофайл `SlapTypes.swift` (26 строк), искусственно отделенный от `SlapDetector.swift`.
  2. Рассогласование порядка элементов кортежей между `KeystrokeBuffer.swift` (`word: String, deleteCount: Int, tail: String`) и `Engine.swift` (`word: String, tail: String, deleteCount: Int`), приводящее к неявному перемешиванию кортежей компилятором (Tuple Shuffle Deprecation).
  3. Неиспользуемые и неизменяемые мутабельные переменные (`var u` в `TextReplacer.swift`, `let nH` в `NotchIsland.swift`, `var w` в `AppBanner.swift`).
- **Decision:**  
  1. Применить паттерн Coalesce Micro-files: слить `SlapTypes.swift` непосредственно в `SlapDetector.swift`, удалив сиротский 26-строчный файл.
  2. Унифицировать сигнатуры `fixTwoLeadingCaps` и `fixTypo` в `Engine.swift`, приведя их порядок к каноническому кортежу буфера `(word: String, deleteCount: Int, tail: String)`.
  3. Устранить мутабельность немодифицируемых переменных и удалить неиспользуемые переменные силуэта.
- **Consequences:**  
  - Сокращение числа сущностей (Fewest Elements) без потери функциональности.
  - Устранение предупреждений компилятора Swift 5 и обеспечение готовности к строгому режиму Swift 6.

## 2026-10-25 ADR-008: Динамический код клавиши ⌘V, потокобезопасность plateCache и адаптация выреза к смене экранов (Батч 3)

- **Context:**  
  Аудит totals-critic зафиксировал остаточные дефекты протоколов уровня P1 и P2:
  1. `TextReplacer.swift`: хардкод виртуального кода `vKey = 9` (ANSI V). На альтернативных раскладках ввода (Dvorak, Colemak, AZERTY) физическая клавиша скан-кода 9 транслируется в символ точки (`.`), превращая `⌘V` в сочетание отмены `⌘.`.
  2. `MenuBarController.swift`: статический словарь кэша подложек `plateCache` модифицируется без синхронизации, создавая потенциальную гонку потоков при фоновом обновлении интерфейса.
  3. `VoiceIndicator.swift`: отсутствие подписки на `NSApplication.didChangeScreenParametersNotification`, вызывающее дрейф выреза и зависание геометрии при подключении внешних дисплеев.
- **Decision:**  
  1. В `TextReplacer.swift` реализовать динамическое вычисление виртуального кода клавиши 'V' через `DynamicKeymap.latinKeyCodes["v"]` с безопасным откатом к ANSI коду 9 при пустой таблице.
  2. Защитить доступ к `plateCache` в `MenuBarController.swift` через экземпляр `NSLock`.
  3. В `VoiceIndicator.swift` добавить подписку на системное уведомление `NSApplication.didChangeScreenParametersNotification` для корректного сброса островка при смене разрешения или мониторов.
- **Consequences:**  
  - Гарантированная вставка через системный буфер `⌘V` на любых латинских и альтернативных раскладках.
  - Полная потокобезопасность рендеринга иконки статуса строки меню.
  - Стабильность геометрии HUD и выреза на мультимониторных конфигурациях.

## 2026-10-25 ADR-009: Параллельное сосуществование Keytamer и Keyboop (неблокирующий singleton lock)

- **Context:**  
  Пользователь выразил однозначное требование: сохранить Keyboop в качестве основной повседневной утилиты ввода на macOS, а Keytamer запускать параллельно как экспериментальную среду для отработки новых фич. Ранее внедренная жесткая блокировка `return false` при занятом `Keyboop/singleton.lock` предотвращала параллельный запуск.
- **Decision:**  
  1. В `AppDelegate.swift` перевести проверку `Keyboop/singleton.lock` из режима блокирующего отказа (`return false`) в режим информационного уведомления с фиксацией в логе.
  2. Замок единственного экземпляра Keytamer удерживается строго в своем собственном файле `Keytamer/singleton.lock`.
  3. Сохранить полную изоляцию хранилищ, логов и настроек между обоими приложениями.
- **Consequences:**  
  - Keytamer и Keyboop могут работать в системе одновременно без конфликтов на уровне файловых замков.
  - Пользователь может гибко развести хоткеи диктовки и режимы автозамены между стабильным Keyboop и экспериментальным Keytamer.

## 2026-10-27 ADR-010: Бесшовная миграция пользовательских настроек из Keyboop в Keytamer

- **Context:**  
  При ребрендинге приложения в Keytamer (`com.keytamer.tamer` / `com.keytamer.tamer.dev`) создаётся изолированный домен `UserDefaults`. В результате пользовательские настройки из `ru.keyboop.app` (авто-отправка после завершения речи `voiceAutoEnter = 1`, модификаторы `voiceAutoEnterMods = 1048576`, движок `voiceEngine = parakeet`, персональные словари опечаток `typoPersonalWords`, текстовые сниппеты `snippetsOrdered` и исключения приложений `appExceptionModes`) не переносились, и Keytamer стартовал со стандартными дефолтами (`voiceAutoEnter = false`), из-за чего надиктованный текст не отправлялся автоматически.
- **Decision:**  
  1. В `AppSettings.swift` добавить метод `migrateFromKeyboopIfNeeded()`, запускаемый при инициализации `AppSettings`.
  2. Метод считывает `persistentDomain(forName: "ru.keyboop.app")` и, если флаг `didMigrateFromKeyboop` ещё не установлен, переносит все пользовательские настройки в `UserDefaults.standard` по принципу «не перезаписывать уже изменённые пользователем ключи в Keytamer».
  3. Исключить из переноса служебные ключи Sparkle (`SU*`), идентификаторы окон и временные метки крэш-сканера.
  4. По завершении переноса фиксировать флаг `didMigrateFromKeyboop = true`.
- **Consequences:**  
  - Сохраняется 100% пользовательских привычек и настроек ввода/диктовки (авто-отправка `voiceAutoEnter`, словари замен, сниппеты, движок `parakeet`).
  - При первом запуске Keytamer у любого пользователя автоматически подхватываются все существующие конфигурации из Keyboop без ручной настройки.

## 2026-10-29 ADR-011: Управление записью (пауза/возобновление), настраиваемая отмена (Command) и вставка 2× Option

- **Context:**  
  Пользователю требуется расширенный контроль над жизненным циклом диктовки:
  1. Возможность ставить аудиозапись на паузу (во избежание записи пауз и лишних звуков) и продолжать её по настраиваемой клавише (по умолчанию Пробел).
  2. Возможность отменять запись не только по клавише Escape, но и по назначенной клавише, в частности по одиночному нажатию клавиши Command (`⌘`).
  3. Возможность вставлять последнюю расшифровку двойным нажатием клавиши-модификатора (2× Option ⌥) с арбитражем задержки относительно одиночного вызова диктовки.
- **Decision:**  
  1. В `AudioRecorder` внедрить потокобезопасные методы `pause()` / `resume()` и флаг `isPaused`: при активной паузе сэмплы CoreAudio отбрасываются без накопления тишины.
  2. В `VoiceController` добавить метод `togglePause()` и трансляцию статуса в `VoiceIndicator` (янтарное состояние паузы).
  3. В `EventTap` при активной записи перехватывать нажатие Пробела (`swallowDown`) и вызывать `togglePause()`.
  4. В `EventTap` в `handleFlagsChanged` реализовать отмену записи по solo tap Command (`⌘`), а также проверку настраиваемой клавиши отмены в `handleKeyDown`.
  5. В `EventTap` внедрить детектор double-tap Option в окне 250 мс для вызова `handlePasteDictationHotkey()` с временным арбитражем одиночного тапа диктовки.
  6. Добавить соответствующие настройки в `AppSettings`, `SettingsWindow` и `L10n`.
- **Consequences:**  
  - Полный контроль над записью без прерывания сессии.
  - Удобная мгновенная отмена записи через `⌘`.
  - Быстрая вставка последней диктовки по 2× `⌥` без необходимости запоминать трехклавишные сочетания.

## 2026-10-29 ADR-012: Ремедиация замечаний totals-critic (DEF-01, DEF-02, DEF-03, DEF-04) и Chunk-Batching Pause

- **Context:**  
  Состязательный аудит `totals-critic` и замечания пользователя выявили следующие дефекты и требования рантайма:
  1. DEF-01 (P0): При 2× Option второй тап Option попадал в блок диктовки и планировал запуск микрофона через окно арбитража поверх вставленного текста.
  2. Задержка арбитража Option 250 мс ощущалась раздражающе долгой при обычном одиночном тапе для запуска диктовки.
  3. Необходимость честной остановки аудио при паузе (Chunk-Batching Pause): микрофон должен полностью останавливаться (`recorder.stop()`), текущий аудио-сегмент отправляется на фоновое распознавание и накапливается в `sessionTextSegments`. При снятии с паузы стартует новый сегмент записи. При окончании диктовки (`end()`) все накопленные сегменты склеиваются в единый непрерывный текст через пробел и единым полотном отправляются на вставку, авто-отправку и в историю.
  4. DEF-02 (P1): Метод `setPaused` в `VoiceIndicator` конфликтовал с периодическим тикером `startTicker()`, который через 500 мс затирал статус «Пауза» секундомером и искажал хронометраж.
  5. DEF-03 (P2): Отмена диктовки по Command срабатывала на событие DOWN (`flagsChanged`), что приводило к моментальному убийству записи при любом служебном аккорде (`⌘C`, `⌘Tab`).
  6. DEF-04 (P2): Отсутствие функциональной симуляции автомата состояний double-tap в тестах `RemediationTests.swift`.
- **Decision:**  
  1. В `EventTap.swift` при детектировании двойного тапа Option выставлять `suppressVoiceOnNextUp = true` и принудительно сбрасывать `voiceModArmed = false`. При следующем `keyUp` флаг снимается без вызова `toggleVoice`.
  2. Снизить окно ожидания второго тапа Option со старых 250 мс до 170 мс (`0.17` с), обеспечив мгновенный отклик на одиночный тап записи.
  3. В `VoiceController.swift` внедрить сегментный батчинг: хранить массив распознанных кусков `sessionTextSegments: [String]`. При `togglePause()` во время записи: останавливать микрофон `recorder.stop()`, отправлять сэмплы на асинхронную транскрибацию и добавлять результат в `sessionTextSegments`. При возобновлении: запускать `recorder.start()`. При вызове `end()`: транскрибировать последний кусок и склеивать все сегменты в единый текст через пробел перед доставкой (`deliver`).
  4. В `VoiceIndicator.swift` останавливать `ticker` при паузе, удерживать надпись «Пауза», а при возобновлении компенсировать длительность нахождения в паузе в `recStart`.
  5. В `EventTap.swift` перевести отмену по Command на solo tap UP: взводить `cmdCancelArmed = true` на `flagsChanged` с Command, сбрасывать при любом `keyDown` (аккорд), и отменять запись строго при чистом отпускании Command.
  6. В `Tests/RemediationTests.swift` добавить симуляцию автомата состояний `EventTapState` для цепочки 2× Option, аккордов Command и сегментной склейки.
- **Consequences:**  
  - Полная надежность жестов без ложных запусков диктовки после вставки.
  - Мгновенный отклик диктовки на одиночный тап Option (170 мс вместо 250 мс).
  - Честная сегментная пауза с батчингом: CoreAudio реально останавливается, фоновая транскрибация прогрессирует, единое полотно текста вставляется без потери слов.
  - Корректное отображение и учет времени паузы в UI выреза.
  - Безопасность нажатия аккордов с Command во время диктовки.
  - Получение финального допуска `ACCEPTED FOR PRODUCTION`.

## 2026-10-29 ADR-013: Универсальные триггеры команд (Single/Combo/Double/Triple) и Zero-Loss сохранение сегментов при отмене

- **Context:**  
  1. Пользователь выявил дефект сохранения сегментов при отмене диктовки: если запись велась с паузами, а затем была отменена (Escape или Command), в `VoiceHistory` попадал только последний хвостовой кусочек аудио, а все предшествующие сегменты уничтожались вызовом `sessionTextSegments.removeAll()` до финализации. При последующей вставке последней диктовки восстанавливался не весь текст, а лишь его фрагмент.
  2. Хардкод клавиш и режимов нажатия недопустим: пауза не должна быть ограничена голым пробелом, отмена — только Escape, а вставка — только 2× Option. Каждая команда обязана гибко настраиваться на любую клавишу, сочетание или режим мульти-нажатия (одиночный, 2× двойной, 3× тройной). По умолчанию для паузы должна использоваться комбинация `⌥Пробел` (Option + Space).
- **Decision:**  
  1. В `VoiceController.swift` исправить метод `cancel()`: не стирать накопленные сегменты до сохранения в историю. При отмене все сегменты сессии (`sessionTextSegments` + `pendingSegmentTasks` + `tailSamples`) дораспознаются, объединяются через пробел и сохраняются в `VoiceHistory` с флагом `historyOnly: true`. Текст не попадает в активное поле ввода, но гарантированно сохраняется целиком и доступен для вставки.
  2. В `AppSettings.swift` и `EventTap.swift` реализовать универсальную архитектуру триггеров для всех команд диктовки:
     - Пауза / продолжение (`voicePause`): режимы `key` (сочетание, дефолт `⌥Пробел`), `modkey` (одиночный модификатор), `doubletap` (2×), `tripletap` (3×).
     - Отмена записи (`voiceCancel`): режимы `key` (Esc), `modkey` (solo Command), `doubletap` (2×), `tripletap` (3×).
     - Вставка последней расшифровки (`pasteDictation`): режимы `doubletap` (дефолт 2× Option), `tripletap` (3× Option), `key` (сочетание).
  3. В `EventTap.swift` внедрить универсальный детектор мульти-нажатий (`MultiTapDetector`) со скользящим окном 180–220 мс для клавиш и модификаторов с поддержкой 1×, 2× и 3× тапов.
  4. В `SettingsWindow.swift` добавить интерфейс выбора режима срабатывания и интерактивной записи хоткеев для каждой команды.
- **Consequences:**  
  - Единая сущность надиктованного сообщения: даже при отмене записи сохраняется 100% надиктованных слов из всех сегментов сессии.
  - Полная свобода кастомизации: любая клавиша, любое сочетание модификаторов, 1×/2×/3× нажатия без ограничений.
  - Пауза по умолчанию работает на эргономичном `⌥Пробел`, не конфликтуя с обычным пробелом при печати.
